## 1. 개요 및 목적
프로젝트가 고도화됨에 따라 아키텍처 설계, 기능 정의서, API 스펙 등 다양한 문서가 생성됩니다. 코드는 Git으로 버전 관리가 되지만, 문서는 적절한 기준이 없으면 다음과 같은 문제가 발생합니다:
* 어떤 문서가 최신(Single Source of Truth)인지 불명확함.
* 과거 설계(As-Is)와 미래 목표(To-Be)가 혼재되어 코드와의 불일치 발생.
* 협업 시 문서 수정 이력 추적의 어려움.

이 가이드는 이러한 문제를 방지하고, 모든 프로젝트 참여자(사람 개발자 및 AI 에이전트)가 통일된 방식으로 문서를 관리하도록 규정합니다.

## 2. 문서 분류 및 관리 방식
문서의 성격에 따라 관리 방식을 다르게 적용합니다.

### 2.0 폴더별 관리 원칙

`docs/`는 문서 성격별 하위 폴더로 관리합니다.

| 폴더 | 역할 | 관리 원칙 |
|------|------|-----------|
| [`../current/`](../current/) | 현재 기준 문서 | 현재 코드와 운영 구성에 맞춰 단일 파일을 지속 갱신합니다. |
| [`../plans/`](../plans/) | 계획/이력 문서 | 리팩토링 계획, 목표 설계, 구현 청사진, 이관 이력을 버전 파일로 보존합니다. |
| [`../governance/`](../governance/) | 문서 관리 규칙 | 문서 분류, 메타데이터, 버전 관리 정책을 관리합니다. |

### 2.1 현재 기준 문서 (Current Source of Truth)
* **현재 프로젝트의 실제 구조와 동작을 확인할 때는 항상 [`../current/ARCHITECTURE.md`](../current/ARCHITECTURE.md)를 먼저 봅니다.**
* `../plans/`의 `ARCHITECTURE_PLAN_v*.md` 파일은 현재 상태를 대체하지 않습니다. 해당 파일들은 계획, 이관 이력, 목표 설계, 구현 청사진을 보존하기 위한 문서입니다.
* 계획이 코드에 반영되면 [`../current/ARCHITECTURE.md`](../current/ARCHITECTURE.md)를 갱신하고, 해당 계획 문서의 상태를 `이관 완료` 또는 `계획 이력`으로 조정합니다.

### 2.2 실시간 동기화 문서 (In-place Maintenance)
* **대상**: 프로젝트 리드미([README.md](../../README.md)), 현재 시스템 아키텍처 현황([ARCHITECTURE.md](../current/ARCHITECTURE.md)) 등.
* **방식**: 별도의 버전 파일(`_v1`, `_v2` 등)을 생성하지 않고, **단일 파일 내에서 내용을 지속적으로 갱신**합니다. 이력은 Git 커밋 로그로 관리합니다.

### 2.3 이정표 및 계획 문서 (Versioning by Filename)
* **대상**: 기능 분할 이관 기록([ARCHITECTURE_PLAN_v1.md](../plans/ARCHITECTURE_PLAN_v1.md)), 리팩토링 목표 아키텍처 설계서([ARCHITECTURE_PLAN_v2.md](../plans/ARCHITECTURE_PLAN_v2.md)), 구현 청사진([ARCHITECTURE_PLAN_v3.md](../plans/ARCHITECTURE_PLAN_v3.md)), 주요 마이그레이션 계획서 등.
* **방식**: 큰 단위의 패러다임 변화나 단계별 아키텍처 목표를 기술할 때는 파일명 뒤에 버전 접미사(예: `_v1`, `_v2`)를 붙여 **별도 파일로 보존**합니다. 이는 과거의 결정 흐름(History of Decisions)을 파악하는 데 유용합니다.

### 2.4 현재 `docs/` 문서 역할

| 문서 | 분류 | 역할 |
|------|------|------|
| [`../current/ARCHITECTURE.md`](../current/ARCHITECTURE.md) | 현재 기준 문서 | 현재 프로젝트의 코드, API, 데이터 모델, 인프라, 알려진 문제를 설명 |
| [`../plans/ARCHITECTURE_PLAN_v1.md`](../plans/ARCHITECTURE_PLAN_v1.md) | 계획 이력 | services 기능 분할 이관 기록 |
| [`../plans/ARCHITECTURE_PLAN_v2.md`](../plans/ARCHITECTURE_PLAN_v2.md) | 목표 설계 | services 계층의 포트/어댑터 목표 구조 |
| [`../plans/ARCHITECTURE_PLAN_v3.md`](../plans/ARCHITECTURE_PLAN_v3.md) | 구현 계획 | v2 목표를 현재 코드에 적용하기 위한 단계별 청사진 |
| [`DOCUMENT_VERSION_CONTROL.md`](./DOCUMENT_VERSION_CONTROL.md) | 관리 규칙 | 문서 분류, 메타데이터, 버전 표기, 협업 규칙 |

## 3. 문서 메타데이터 표준
모든 마크다운(`.md`) 문서의 최상단에는 아래 양식의 메타데이터 헤더를 반드시 기입해야 합니다.

```markdown
# [문서 제목]

> 버전: [X.Y] · 최종 갱신: [YYYY-MM-DD] · 브랜치: `[branch-name]` · 상태: **[상태]**
> 문서 역할: [현재 기준 문서 / 계획 문서 / 버전 관리 문서 등 역할 설명]
```

### 메타데이터 필드 상세
* **버전 (Version)**: 문서의 버전 번호 (예: `1.0`, `1.1`).
* **최종 갱신 (Last Updated)**: 문서가 마지막으로 수정된 날짜 (`YYYY-MM-DD`).
* **브랜치 (Branch)**: 해당 문서의 기준이 되는 Git 브랜치명 (예: `dev/ai`).
* **상태 (Status)**:
  * **현재 현황 (Current / Source of Truth)**: 현재 코드와 운영 구성을 설명하는 기준 문서.
  * **초안 (Draft)**: 작성 중이며 아이디어 구체화 및 논의가 필요한 상태.
  * **검토 중 (Review)**: 피드백 수렴 및 리뷰어 승인을 기다리는 상태.
  * **승인됨 (Approved)**: 협업 과정에서 합의가 완료된 상태.
  * **계획 이력 / 이관 완료 (Implemented Plan)**: 제안된 스펙이 코드로 구현되어 이력으로 보존되는 상태.
  * **계획 문서 / 목표 설계 (Target / To-Be)**: 향후 리팩토링이나 기능 추가 시 도달해야 할 지향점.
  * **계획 문서 / 구현 준비 청사진 (Implementation Plan)**: 목표 설계를 실제 코드에 적용하기 위한 단계별 실행 계획.
  * **폐기 (Deprecated / Archived)**: 더 이상 유효하지 않지만 참고용으로 보관하는 문서.

## 4. 문서 버전 표기 규칙 (Semantic Versioning)
문서의 버전 번호(`X.Y`)는 소프트웨어의 유의적 버전(SemVer)을 단순화하여 적용합니다.

* **Major 버전 상승 (`X.0`)**: 
  * 시스템 아키텍처 패러다임 전환 (예: 단일 레이어 구조 -> 포트 및 어댑터 아키텍처 전환).
  * 시스템 전반의 핵심 정책 및 도메인 모델 개편.
* **Minor 버전 상승 (`+0.1`)**:
  * 특정 도메인의 하위 모듈 분할/이관 계획 추가.
  * 기존 구조를 유지한 상태에서 새로운 시나리오나 흐름 추가.
* **패치/단순 수정 (`버전 유지` 또는 날짜만 갱신)**:
  * 오탈자 수정, 가독성 개선, 파일 링크 연결 등 경미한 변경.

## 5. Git 브랜치 및 커밋 전략
* **코드와 문서의 동시 변경**: 코드 변경 사항이 문서(예: API 변경)에 영향을 미치는 경우, **동일한 커밋 또는 동일한 PR(Pull Request) 내에 코드와 문서 수정을 함께 포함**해야 합니다.
* **커밋 메시지 규칙**: 문서 작업에 대해서는 `docs` 프리픽스를 명확히 사용합니다.
  * 예: `docs: 문서 버전 관리 가이드 추가`
  * 예: `docs: ARCHITECTURE.md 에 Celery 태스크 구조 현행화`
* **브랜치 전략**: 문서 수정 역시 해당 기능 브랜치(예: `dev/ai`)에서 진행 후 승인을 받아 메인 브랜치로 병합(Merge)합니다.

## 6. AI 에이전트 협업 규칙
본 프로젝트는 AI 코딩 에이전트와 긴밀하게 협업합니다. AI 에이전트는 문서 작성 및 수정 시 다음 규칙을 엄격히 준수해야 합니다.

1. **기존 주석 및 메타데이터 보존**: 문서를 수정할 때 기존 문서에 포함된 의사결정 맥락, 주석, 기존 개발자의 코멘트를 임의로 삭제해서는 안 됩니다.
2. **헤더 갱신 의무**: 문서를 생성하거나 수정할 때는 반드시 최상단 메타데이터 헤더의 **최종 갱신 일자(Last Updated)**, **버전(Version)**, **상태(Status)**를 현재 작업 내용에 맞춰 업데이트해야 합니다.
3. **가독성 및 파일 링크 제공**: 문서 내에서 프로젝트의 다른 파일이나 코드를 참조할 때는 마크다운 링크 형식을 사용하며, 저장소 안에서는 상대 경로를 우선 사용합니다.
4. **현재/계획 구분 유지**: 현재 코드 설명은 `docs/current/ARCHITECTURE.md`에 반영하고, 계획·이력·청사진 문서는 `docs/plans/`에 둔 뒤 상단 메타데이터와 본문에서 문서 역할을 명확히 표시해야 합니다.
